\section{前沿不是清单：围绕同一制品的四个控制回路}
\label{sec:frontiers}

把“验证编译、机器学习优化、超优化、JIT、可复现构建”逐项介绍，很容易成为与案例脱节的名词目录。更有解释力的组织方式，是问同一个截断点积在编译系统中面对哪一种不确定性：\emph{语义回路}检查变换有没有改错；\emph{搜索回路}在许多合法程序中选代价较小者；\emph{经验回路}用运行事实修正静态猜测；\emph{制品回路}保证计算结果能正确复用并由他人重建。四个回路互补而不相互替代，如表~\ref{tab:four-loops} 所示。

下面每一小节均回到三个问题：主张的关系是什么，生产系统已有多成熟，什么观察会推翻推荐。成熟度不是“论文新旧”的同义词：本文用 P1 表示原型/概念验证，P3 表示可控场景中可部署但集成代价显著，P5 表示在明确适用域内已有大规模生产经验。

\subsection{先证明合法，再讨论快慢：验证编译与翻译验证}

令源程序为 $S$，编译器为 $C$，目标为 $T=C(S)$，$\mathrm{Beh}(P)$ 为给定语言语义下的可观察行为集合。优化编译通常需要行为细化（behavioral refinement）而非文本相等：
\begin{equation}
 C(S)=T \Longrightarrow \mathrm{Beh}(T)\preceq \mathrm{Beh}(S).
 \label{eq:refinement}
\end{equation}
关系方向取决于未定义行为、非确定性、发散与 I/O 如何建模。前文几组输入输出相等只是有限测试证据，远弱于式~\eqref{eq:refinement}。

CompCert 代表\emph{验证编译器}（verified compiler）：其核心从类型化 C AST 到汇编 AST 的多道变换在 Coq/Rocq 中逐 Pass 证明语义保持\cite{adv-compcert-cacm,adv-compcert-site}。中间语言在这里是证明接口。然而可靠主张必须连同边界一起说：预处理、部分前端处理、汇编文本打印、汇编与链接等并不自动包含在核心定理内；形式源/目标模型、ABI 和外部工具仍属于可信计算基（trusted computing base）\cite{adv-compcert-tcb}。因此 CompCert 在高保证嵌入式 C 中可视为 P4，但不是对 Clang/GCC 全生态的即插即用替代。

翻译验证（translation validation）换一个分工：不证明复杂优化器实现，而对每次产生的源/目标对做检查。Alive2 把 LLVM IR 的细化失败编码给 SMT 求解器，可为某些错误重写给出具体反例；它已经用于 LLVM 优化开发，但论文准确称其为\emph{有界}翻译验证\cite{adv-alive2}。循环界、内存模型、未支持操作和超时决定结论范围。报告必须区分“验证通过”“反例推翻”“未知/超时”“不支持”，后二者不是正确性证书。经验证验证器（verified validator）更进一步：搜索可不受信任，小而稳定的检查器具有机器证明；CompCert 的指令调度验证器展示了这种结构\cite{adv-verified-validator}。

对本文点积，合理的实验不是宣称整个二进制被证明，而是截取一次 LLVM 变换前后的 IR，固定 LLVM/Alive2/求解器版本，检查细化；再构造一个违反溢出或 poison 前提的错误重写，要求验证器产出反例。若操作不被支持、求解超时，或源程序本身依赖未定义行为，则该实验不能支持语义保持。学术前沿追求更广的形式覆盖；生产最佳实践则是把验证器放在高风险重写和回归测试旁边。这两者并不冲突：前者缩小模型缺口，后者先在收益最大的边界落地。

\subsection{扩大候选空间：多面体、超优化与等式饱和}

本文点积的循环界和数组下标是仿射的，主体接近静态控制部分（static-control part, SCoP）。多面体模型（polyhedral model）用整数仿射约束描述迭代域、访问和依赖，再把调度表示成仿射映射；循环交换、融合、偏斜、分块和并行化由此成为约束下的搜索。Pluto 证明了整数线性优化可形成实际自动并行/局部性流水线\cite{adv-pluto}，LLVM Polly 与 MLIR Affine/Linalg 则是生产与多层 IR 的桥梁\cite{adv-polly}。但间接寻址、数据相关边界、不透明调用、别名和不规则控制会打碎 SCoP；运行时守卫可以恢复部分机会，也会引入开销。独立评估观察到速度提升之外还有健壮性与正确性失败，说明“可建模”不等于“目标上有收益”\cite{adv-polyhedral-survey}。规则密集数值核可评 P3--P4，任意 C/C++ 自动并行仍更接近 P2--P3。

超优化（superoptimization）从有界程序空间寻找语义等价且成本最小的程序。STOKE 对短 x86-64 序列做随机搜索，Souper 为 LLVM 整数 SSA 片段综合重写；二者的重要生产启示不是把无界搜索塞进每次构建，而是“离线发现---独立验证---纳入普通重写”\cite{adv-stoke,adv-souper}。这样把昂贵探索摊销掉，也让编译时延可预测。其失败条件清楚：状态/序列空间爆炸，验证仅覆盖测试或有界模型，成本函数与真实硬件不一致。

等式饱和（equality saturation）改变的则是重写表示。e-图（e-graph）紧凑表示表达式上的同余关系；重写先把等价候选加入图中，最后按成本抽取，从而推迟破坏性的次序选择。\code{egg} 的重建与 e-class 分析使该方法成为可复用系统\cite{adv-egg}。但它消除的只是\emph{已纳入等式之间}的阶段次序问题：图会增长，具有共享/环和全局寄存器压力的最优抽取本身可能困难；浮点、溢出、LLVM poison、别名和副作用的前提仍须单独证明。Cranelift 的生产化尤其有启发：其采用嵌入 CFG 的无环 e-图、规则 DSL、燃料上限、效果边界、启发式成本与模糊测试，而不是对通用库无限饱和\cite{adv-cranelift-egraph}。通用饱和可评 P2--P3，受限域中的 Cranelift 实现已接近 P4。

在截断点积上，可以把截断后的整数子表达式送入 e-图，同时分别用指令数和目标延迟/代码大小抽取。若二者选择不同，恰好说明“相等”是语义问题，“最好”是经验问题。任何利用外层加法结合律的规则都必须引用先前证明的结果界 $[-64,96]$；把逐项截断错误地移到求和之后，或把程序推广到未证明的新长度/输入域，都会使该依据失效。搜索空间越大，越需要上一小节的验证回路，二者不是竞争技术。

\subsection{从测量中学习：PGO、MLGO 与分布漂移}

配置文件引导优化（profile-guided optimization, PGO）不是一个孤立开关，而是因果回路：
\[
 \text{构建}\rightarrow\text{插桩/采样}\rightarrow\text{代表性负载}
 \rightarrow\text{配置文件}\rightarrow\text{重建/重排}\rightarrow\text{独立评估}.
\]
Clang 同时支持插桩式与采样式 PGO，数据会影响分支布局、内联等决策；官方文档也明确警告训练负载必须具有代表性\cite{adv-clang-pgo}。AutoFDO 用硬件采样降低采集摩擦，BOLT 在最终二进制地址和布局已确定后依据剖面重排代码；这些系统在 Google、Meta 等生产负载上的证据使 PGO 达到 P5、BOLT 在满足二进制和调试/重定位条件时达到 P4\cite{adv-autofdo,adv-bolt}。

最常被忽略的威胁是分布漂移（distribution shift）。若训练输入服从 $P_{\mathrm{train}}(x)$，部署服从 $P_{\mathrm{deploy}}(x)$，那么对前者优化后的收益能否迁移，是额外推断而非编译器定理。本文的小规模边界用例能验证语义，却不能代表真实热度；若训练几乎总为 $n=8$，部署却大量出现 $n=0$ 或错误边界，布局和内联决策可能适得其反。最低限度应分开训练集、同分布留出集和主动偏移集，报告运行时间分布、尾延迟、代码大小、采集/构建成本与冷启动；同一批运行既训练又报分数会乐观偏置。

机器学习引导优化（machine-learning-guided optimization）适合替换一个收益启发式，不应替换语义合法性。LLVM MLGO 已提供面向内联大小和贪心寄存器分配驱逐等决策的基础设施，训练编排在 LLVM 外部；相关工作报告了特定任务上的代码尺寸收益，但不能外推为“ML 自动解决阶段排序”\cite{adv-mlgo-paper,adv-mlgo-doc}。公平比较必须使用同版本强基线与相同编译预算，训练/测试项目去重，计算特征提取、推理、失败编译和维护成本，并观察跨架构、跨编译器版本的尾部退化。若强 PGO 基线在留出项目/目标上追平模型，或漂移后的回归超过收益，学习策略的部署假设即被证伪。基础设施约 P3，具体、受监控的已发布策略可达 P3--P4；广义生成式优化仍是 P1--P2。

PGO 与 MLGO 也并非二选一：静态特征描述代码“是什么”，剖面描述部署时“怎样运行”。两者都必须把程序版本、IR 模式、目标、编译器修订、特征提取器以及工作负载种群当成有版本的优化输入；否则模型或 profile 的陈旧会被误诊成随机性能波动。

\subsection{异构编译：表示解决合法性，调度决定收益}

第~\ref{sec:mlir} 节已经说明，多层 IR 通过保存形状、归约维、布局和地址空间，避免从低层代码重建领域知识。多面体调度、显式 schedule 语言与异构后端进一步回答“在哪种层级、以多大块、在哪个计算单元执行”。TVM 把计算和 schedule 分开并通过自动调优覆盖多种后端，Halide/Tiramisu 也展示了显式调度在图像与张量领域的价值\cite{adv-tvm,adv-halide,adv-tiramisu}。这些结果支持“结构与调度分离”这个机制，却不支持一次 schedule 跨硬件无损迁移。

点积在 CPU 上可能被向量化为连续载入和树形归约；在 NPU 上则需要 GM--片上搬运、tile、部分和以及跨核合并。表示能说清候选是否合法，成本模型和真实测量才判断是否值得。一个严格实验应只改变 tile/向量/映射参数，同时分开测量编译、传输、冷启动、稳态吞吐和内存；若候选越界、需要过多同步，或在未参与调优的输入/设备上退化，便否定“性能可移植”的强主张。MLIR 基础设施可评 P4，但每个下游方言栈从 P1 到 P5 不等，不能把核心工程成熟度传递给任意厂商后端。

更前沿的方向是把变换策略本身表示成 IR，例如 MLIR Transform dialect，以便组合、参数化并作用于载荷 IR；它提高可检查性，却没有消除 schedule 工程和成本模型\cite{adv-transform-dialect}. 学术界在探索可组合搜索空间和跨层验证，生产系统更看重有界编译时间、硬件快速演进与可诊断失败。实际建议是：先保留足够高层语义，再在明确设备和负载上逐步收窄选择，不把自动调优的最好一次运行冒充普遍性能。

\subsection{何时编译：AOT、JIT 与混合分层}

预先编译（ahead-of-time compilation, AOT）和即时编译（just-in-time compilation, JIT）的真正轴线是“信息何时可得”。AOT 知道源、静态目标和可选离线 profile，换来可预测部署、启动和一次性优化成本；JIT 能看到运行类型、真实热度、微架构和动态链接状态，却要支付预热、编译 CPU/内存、代码缓存和去优化元数据。分层编译（tiered compilation）先解释或快速生成基线代码，再把热路径提升到优化层，用更多状态复杂度换启动与峰值的折中。

Android ART 同时使用解释、JIT、AOT 和 profile，引导模式把这种折中变成产品策略；LLVM ORC 提供惰性/并发物化、JIT 链接和跨进程等基础设施\cite{adv-art-jit,adv-orc}. 因而“AOT 或 JIT 谁更快”是错误问题：同一个点积若只运行一次，JIT 编译时间很可能压倒执行；若在长寿命服务中以稳定类型运行数百万次，动态特化才可能偿还成本。AOT 与成熟管理运行时的分层 JIT 均为 P5，ORC 作为基础设施约 P4，但新语言自行构建去优化、GC 与调试体系仍可能只有 P2。

公平测量要分开进程启动、首次响应、基线层执行、编译 CPU 与峰值内存、达到稳态所需请求数、稳态吞吐/尾延迟、代码缓存与失效、安装制品大小。若 JIT 的“胜利”排除了预热而 AOT 计入启动，比较即被证伪。对本课程的短程序，画清符号物化、编译、运行时链接与代码内存，比为了一个玩具加速比搭建完整 JIT 更有科学价值。

\subsection{全局可见性、快速迭代与可重建制品}

链接时优化（link-time optimization, LTO）让跨翻译单元内联和全程序分析成为可能，但完整合并会消耗时间和内存，也削弱并行增量工作。ThinLTO 的工程答案是紧凑模块摘要：链接时建立全局摘要索引、做导入等决策，再并行运行每模块后端并缓存结果\cite{adv-thinlto-paper,adv-thinlto-doc}。它不是“既全局又零成本”的魔法；摘要会牺牲某些精度，函数导入扩大失效集合，平台/链接器支持也不同。对大型 LLVM 系生产构建可评 P5。

LTO 与 BOLT 观察的世界不同：前者拥有类型和 SSA，可改变调用与计算；后者看到最终地址、对齐、链接进来的库和实测布局。LLVM 的高级构建文档组合 PGO、ThinLTO 与 BOLT，恰好说明它们是不同时间点的互补反馈\cite{adv-llvm-advanced-builds}。若要在点积案例中展示 LTO，应故意分成调用者与核函数两个翻译单元，比较普通 \code{-O2}、全 LTO、ThinLTO、ThinLTO+PGO，并记录导入、缓存命中、增量链接时间和峰值内存；单文件中宣称观察到“跨模块收益”没有可证内容。

增量性（incrementality）与可复现性（reproducibility）检验的是两个不同关系。前者问一次编辑后能否复用未受影响结果而不陈旧；后者问固定的声明输入与环境能否得到逐位相同制品。\code{rustc} 把编译表示为查询及依赖 DAG，以 red--green 算法在输入未变或重算结果相同时阻止不必要传播\cite{adv-rust-incremental}；“Build Systems à la Carte”则用任务、调度、依赖与缓存选择统一分析构建系统\cite{adv-build-systems}。正确缓存键必须包含源码和生成文件、工具版本、选项、目标、会影响结果的环境、插件及依赖输出。少记一个输入会错误命中，多记只会损失性能。

可复现构建要求相同源、构建说明和环境产生相同输出；时间戳、路径、区域/时区、遍历顺序、随机数和归档元数据都是常见干扰，\code{SOURCE\_DATE\_EPOCH} 只解决其中一个通道\cite{adv-repro-docs,adv-repro-paper}。逐位一致能支持第三方核对发布制品与声明输入，却不证明源是良性的、编译语义正确或两个构建者彼此独立。这里没有必要把它包装为泛化“安全”：本节处理的明确错误模型是\emph{遗漏输入导致陈旧缓存}与\emph{未声明环境导致二进制不可重建}。

两项验收可以写成：
\begin{align}
 \mathrm{Artifact}(\mathrm{incremental}(e),E)
   &\stackrel{?}{=}\mathrm{Artifact}(\mathrm{clean}(e),E),\\
 \mathrm{Artifact}(\mathrm{clean}(e),E)
   &\stackrel{?}{=}\mathrm{Artifact}(\mathrm{clean}(e),E').
\end{align}
第一式检验失效/缓存正确性，第二式要求 $E$ 与 $E'$ 在已声明维度上等价。不同位应被诊断而非盲目归一化，因为非确定性可能暴露构建工具的数据竞争或隐藏输入。文件/模块缓存已是 P5，细粒度编译器查询在 Rust 等系统中约 P4；整个生态逐位复现则随发行与环境纪律处于 P3--P5。

几条连接比任何单项排名更重要。第一，搜索越激进，语义检查越应独立：超优化、e-图和学习策略可以产生候选，但验证器决定能否接纳。第二，profile 与模型是构建输入，必须与程序、目标和编译器版本共同进入制品回路。第三，多层 IR 保存了优化信息，也扩大了需要定义和验证的语义表面。第四，全程序可见性与快速增量天然拉扯，ThinLTO 的摘要/选择性导入是工程折中而非理论消除。第五，JIT 与 PGO 是把反馈放在不同时间点：一个接近运行过程，一个把运行证据带回下一次 AOT。

对本文的最终建议因此很朴素：保留截断点积的数值与边界不变量；在每个 IR 边界说明语义关系；只在固定成本模型和目标下比较候选；把训练、profile 与硬件视为可能漂移的数据；最后让干净构建、增量构建和声明等价环境下的构建能够相互核对。若未来实验不能通过这些反证条件，正确结论应是缩小主张，而不是再添加一个流行术语。编译研究真正的前沿，不是“用了最新技术”，而是让合法性、收益、适配与制品这四个回路在现实约束下同时闭合。
